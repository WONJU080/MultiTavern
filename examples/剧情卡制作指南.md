# MultiTavern 剧情卡制作指南（给 AI 的完整说明书）

**这份文件是给 AI 助手读的。** 把本文件整份发给 AI，再附上你的素材——SillyTavern 剧情卡（JSON / PNG 导出的文本）、世界书、预设、小说片段，或一段口头叙述的剧情概要——它就能产出一张可直接导入 MultiTavern 的**剧情卡**（`.anyworld.json`）。

**剧情卡是什么**：一个 JSON 对象，建房页点「导入配置」即可加载（导入是**合并**，不会清空已填内容）。它描述整局游戏的剧情底稿、角色池、世界结构、时间轴、插件与生成预设。它同时也是**导出格式**：在同一个表单点「导出配置」得到的就是同一种文件，可以反复复用与分享。

**与 `examples/plot-to-config-prompt.md` 的关系**：那份是「只转换剧情、不产出角色卡」的精简指令，适合已有角色池的房间。**本文件是完整版说明书**：包含角色卡（`characters`）、地区/物品（`regions` / `items`）、插件（`plugins`）、严格时间轴（`schedule`）等全部能力，以及每个字段在游戏里**真正会触发什么行为**。需要完整能力时用本文件。

**配套文件**：`examples/剧情卡生成提示词.md` 里有可直接复制粘贴的「转换提示词」模板（素材完整版 / 口述概要版），它引用本说明书；如果你不想自己写指令，用它开头即可。

## 第一部分 · 给 AI 的工作守则

### 1. 你的任务

把用户提供的素材改写成一个**合法的 JSON 对象**，能被 MultiTavern 建房页的「导入配置」直接读取。

### 2. 输出格式（不可协商）

1. **只输出 JSON 本身**：不要 markdown 代码围栏，不要注释，不要在 JSON 前后写任何解释、标题或收尾语。
2. **双引号、无尾逗号、无 `null` 占位**。没有内容的字段**直接省略**，不要写空字符串或空数组凑数。
3. **不要发明字段。** 本项目使用 Pydantic 严格模型，未知字段、拼错的大小写（如 `Prompt_Blocks`、`timeConfig`）、未知枚举值、把数字写成字符串（`"30"` 而不是 `30`）都会导致**整份配置被拒绝**。
4. 文本语言与素材保持一致，专有名词保留原文。
5. 列表里的对象只允许出现本说明书中列出的键名。

### 3. 取材原则

- **按素材内容决定包含哪些可选字段**，不必填满结构。没有对应内容的字段直接省略。
- **不要为了填满结构而编造重要设定**。可以补全合理的细节（人名、地名、氛围），但核心真相、结局与关键人物关系必须以素材为准；素材没给的信息宁可留白，让 AI 主持人在游戏里自由发挥。
- 优先**少而精**：`lorebook` 和 `prompt_blocks` 越多越占上下文预算，重复、近义的条目应合并。
- 素材里出现的角色卡内容（`description` / `personality` / `mes_example`）现在**可以**转成 `characters`——但请先读第 4 节的角色卡写法，人物必须能支撑多人分头行动。
- 剧情关键但玩家不扮演的 NPC **不要**放进 `characters`（那会让玩家认领到他们）。写进 `scenario`、`guidance` 或 `lorebook`。

### 4. 自检清单（输出前逐条核对）

- [ ] JSON 能被 `json.loads` 解析（无尾逗号、无注释、无围栏）。
- [ ] `scenario` 存在且非空。
- [ ] 数组中的每个对象只用了本说明书列出的键。
- [ ] 所有字符串长度、数字范围、数组条数都在限制内（见第十五部分）。
- [ ] 所有 id 引用闭合：`regions[].items` 指向存在的 `items[].id`；`regions[].links[].to` 指向存在的 `regions[].id`；`links[].requires_item` 指向存在的物品；`events[].region` 指向存在的地区；`world.start_region` 指向存在的地区；`plugins[].config.questions[].event_name` 指向存在的 `events[].name`。
- [ ] 若输出了 `regions` → 必须有 `world.start_region`，且**不要**写 `schedule`（服务器会自动设为 `strict`），并确保 `time_config.enabled = true`。
- [ ] 若输出了任何**纯时间事件**（没有 `region`）→ 必须 `time_config.enabled = true`。
- [ ] 角色名、地区 id、物品 id、事件名在各自范围内**没有重复**（地区 id 与物品 id 不区分大小写）。
- [ ] 布尔字段是真布尔值（`true` / `false`），不是 `"true"`；**没有值的键一律省略，不要写 `null`**（见 14.1）。
- [ ] 数字是真数字（`30`），不是字符串（`"30"`）。
- [ ] `sampling` 只写素材明确给出的值。

## 第二部分 · 输出结构总览

```jsonc
// 以下注释仅供阅读；真实输出必须是纯 JSON，不能带注释。
{
  "scenario": "……",              // 必填：剧情底稿（后台，玩家看不到）
  "opening": "……",               // 可选：固定开场白（会原样展示给玩家）
  "guidance": "……",              // 可选：主持私密手册（后台）
  "characters": [ /* ... */ ],    // 可选：角色池（房主与玩家认领）
  "host_character": "角色名",      // 可选：房主自己要扮演的角色（须在 characters 中）
  "time_config": { /* ... */ },   // 可选：游戏内时钟
  "time_rules": [ /* ... */ ],    // 可选：每轮耗时参考表
  "events": [ /* ... */ ],        // 可选：定时 / 进入地区触发的事件
  "world": { "start_region": "id" },  // 有 regions 时必填
  "regions": [ /* ... */ ],       // 可选：地区图（自动启用严格时间轴）
  "items": [ /* ... */ ],         // 可选：物品（配合 regions 使用）
  "lorebook": [ /* ... */ ],      // 可选：关键词触发的世界书
  "prompt_blocks": [ /* ... */ ], // 可选：固定位置的提示块
  "sampling": { /* ... */ },      // 可选：采样参数
  "plugins": [ /* ... */ ],       // 可选：房间插件（目前只有「可能的真相」）
  "random_turn_order": true,      // 可选：每轮是否随机打乱行动顺序（默认 true）
  "schedule": "round"             // 可选：调度方式；有 regions 时不要写
}
```

**没有标题字段**：标题由 AI 在开局前另行生成。**没有**世界状态、存档位、骰子配置等字段。

### 最常需要省略的字段

| 情况 | 该怎么做 |
| --- | --- |
| 不含时间推进的剧情 | 省略 `time_config` / `time_rules` / `events` |
| 不需要空间探索（对话、室内、单场景为主） | 省略 `regions` / `items` / `world` —— 这正是默认的「回合制」模式 |
| 素材没提采样参数 | 省略 `sampling` |
| 没有额外主持要求 | 省略 `guidance` |
| 没有可触发条目 | 省略 `lorebook` |

## 第三部分 · 剧情三件套：`scenario` / `opening` / `guidance`

这三个字段最容易混淆，先讲清**谁看得到什么**：

| 字段 | AI 可见 | 玩家可见 | 存档（HTML 记录） |
| --- | --- | --- | --- |
| `scenario` | ✅ 作为「初始情景」常驻上下文 | ❌ **永远看不到** | ✅ 原文记录 |
| `opening` | ✅ 作为「已发生的公开开场」 | ✅ 原样展示 | ✅ 原文记录 |
| `guidance` | ✅ 标记为 PRIVATE | ❌ **永远看不到** | ✅ 原文记录 |
| `characters` | ✅ 作为角色卡常驻上下文 | ✅ 角色名与设定可见 | ✅ |

> **玩家能看到的剧情文字只有两处**：`opening`（若提供）或 AI 据此生成的开场，以及每回合 AI 写出的叙事。`scenario` 里的内容**必须由 AI 在游戏过程中逐步揭示**——玩家不会预读到底稿。

### 3.1 `scenario`（必填，1–500,000 字符）

这是**房主侧的后台剧情底稿**，是 AI 的「初始情景」设定书，也是整局游戏的唯一权威设定来源。可以放心写剧透、真相与结局条件。

**推荐结构**（建议用【小标题】或加粗标签分段，AI 更容易定位）：

```
【剧情：《作品名》】
世界与舞台：时代、地点、氛围、世界的特殊规则（魔法/科技/社会制度）。
当前局势：故事开始时正在发生什么；紧张点与倒计时。
玩家方：玩家是谁、彼此什么关系、手头有什么、权限或资源如何。
目标与利害：玩家要达成什么；失败会失去什么；有哪些明确限制。
关键 NPC：名字 + 身份 + 一两句性格与立场（文字描述，不是角色卡）。
基调：文风方向（冷硬悬疑 / 温情日常 / 荒诞喜剧…）。
```

**关键写作要求**：

- **明确写出玩家方要做什么、为什么重要、有什么代价。** 开场生成会专门提取「目标与利害」，写成玩家读得懂的钩子；如果素材里只写了氛围没写目标，AI 会按提示补一个「眼前的契机」，但那样不如你直接写清。
- **写清玩家感知得到的限制**：锁着的门、有限的经费、宵禁、不可逆的时限。这些是让玩家做出有意义选择的东西。
- 建议精炼到必要信息。不要把整本设定原样堆进去——`scenario` 常驻上下文，越冗长越挤占后续回合的预算。
- 铺垫线索顺序：**结论要在证据之后出现**，可以在 `scenario` 里明确要求这条原则。

### 3.2 `opening`（可选，0–500,000 字符）

**固定开场白。** 填写后**原样**作为开场展示给玩家，**不再由 AI 生成**。

**什么时候写它**：素材里有现成的高质量开场文（SillyTavern 的 `first_mes`），或你希望开场一字不改。**什么时候省略它**：想让 AI 根据 `scenario` + 角色池现场生成开场（默认行为，更贴合临场角色）。

**填写时必须**：

- 这是玩家读到的**第一段文字**，应当自带完整设定：场景、气氛、眼前发生的事。
- **让每个玩家角色都出场并各有动作**（若提供了 `characters`）。玩家认领角色后，那段文字里如果完全没有他的角色，会很突兀。
- 系统的开场要求是：不要提前泄露 `guidance` 与隐藏真相，只写角色能知道的事。
- 写完后，这段文字会被当作**既成事实**常驻上下文，之后 AI 不会再重写它。

### 3.3 `guidance`（可选，0–500,000 字符，有隐藏内容时强烈建议）

**主持私密手册**：仅 AI 与存档可见。系统会把它标记为 PRIVATE，要求 AI 不得引用、解释或泄露；AI 输出中若**直接照抄 guidance 原文**，会被校验机制拦下并重试（注意：这道防线拦不住任意改写，所以别把「必须保密」全押在它身上）。

**推荐内容**：

```
一、绝对保密：哪些是幕后真相，在剧情把线索摆上台面前，任何角色不得说破。
二、主线真相：真凶、动机、手法、关键物证的藏匿点。
三、结构与时限：分几幕；哪些时刻会发生什么；错过会永久失去什么。
四、公平推理原则：线索必须先于结论出现；检定只用于获取证据与压力，不直接给答案。
五、NPC 私密动机：谁在撒谎、为什么撒谎、谎言有什么破绽。
六、节奏建议：每幕怎么推进；何时收束；结局分支怎么判。
七、尺度与边界：内容分级、禁止描写的方向。
```

**素材没有额外主持要求时，整个字段省略。**

## 第四部分 · `characters` 角色池与 `host_character`

角色卡塑造的不只是性格，更是**玩家在游戏里唯一能操控的抓手**。写得好不好，直接决定这局能不能玩下去。

### 4.1 字段

| 键 | 必填 | 上限 | 作用 |
| --- | --- | --- | --- |
| `name` | ✅ | 40 字符 | 角色名，**房间内唯一**（不区分大小写） |
| `description` | | 50,000 | 身份、来历、外貌、能力、与剧情的关系 |
| `personality` | | 10,000 | 性格、价值观、行为倾向 |
| `style` | | 10,000 | 说话方式、用词习惯、语速语气 |
| `example_dialogue` | | 10,000 | 几句台词示例，最能让 AI 抓住声线 |

角色数量上限由服务器的 `server.max_characters` 决定（schema 默认 6，**本仓库 `config.yaml` 设为 7**，最大可配到 100）。写 3–6 个是常见规模。

> ⚠️ `characters` 是**必填且至少 1 个**；导入含 `characters` 的配置会**清空现有角色池**再重建。

### 4.2 多人游戏的角色设计原则

这是多人跑团，不是单人 RP。设计角色时**必须让每个角色都能独立行动、各有专长、互不重叠**：

- **每人一条能力主线**：现场勘查 / 问话线人 / 档案账册 / 潜伏潜入 / 交涉谈判 / 战斗护卫。避免三个都是「擅长战斗的独行侠」。
- **每人一个私人牵挂**：一个不愿提的过去、一个要保护的人、一笔旧债。这是玩家之间产生互动的燃料。
- **留出提问空间**：让角色有「必须向别人求助才能做到」的领域，玩家才会互相提议与协作。
- **不要写死角色的立场结论**。写动机和处境，不写「他最终会背叛队伍」——那应该放 `guidance`。
- **给出具体的行为习惯**（「进门前先数出口」「记笔记时反复核对时间」），比抽象形容词（「很聪明」）有用得多。
- **不要在角色卡里写玩家的行动**：例如「他一定会去地窖」。角色卡是设定，不是剧本。

### 4.3 名字是第一契约

系统的结算、骰点计划、回合队列、角色认领、存档**全部以角色名字符串为键**。因此：

- 一旦开局，**不要改名**（改名会让存档里的历史结算对不上）。
- 名字要短、好打、好认；避免近义变体（「甲」与「阿甲」会被当成两个人）。
- 名字最好在同局内彼此差异明显，避免「李雷」「李蕾」这种只差一字的组合。

### 4.4 `host_character`

房主自己要扮演的角色名（字符串，≤40 字符）。**必须精确匹配 `characters` 中的某个 `name`**，否则整份配置被拒绝。房主不打算扮演时，省略此字段。若省略，房主进房后从角色池里自行勾选。

### 4.5 未被认领的角色

**不是浪费**。开局时所有角色都会被介绍出场；未被认领的角色由 AI 托管扮演，是**DM 控制同伴**。玩家中途加入可以认领他们（下一轮起生效，AI 会叙述交接）。所以：**宁可有 1 个留白角色，也不要为了凑人数写空洞角色**。

## 第五部分 · `time_config` / `time_rules` / `events` 时间系统

**只有剧情真正依赖时间时才启用**（倒计时、日程、宵禁、节日、探索耗时、证人会被转移……）。不涉及时间推进的剧情，这三个字段全部省略。

### 5.1 `time_config`

| 键 | 类型 | 省略该键时 | 显式写出时的合法范围 |
| --- | --- | --- | --- |
| `enabled` | 布尔 | `false`（必须显式写 `true` 才启用时钟） | 只能是 `true` / `false` |
| `start_day` | 整数 | `1` | 0–100,000 |
| `start_minute` | 整数 | `390`（06:30） | **0–1439**；从午夜起的分钟数，`19:00` = `1140` |
| `max_elapsed_minutes` | 整数 | `600` | 0–525,600；单轮耗时的硬上限 |
| `default_elapsed_minutes` | 整数 | `15` | 0–525,600；AI 未估出耗时时的默认推进 |

> **注意「省略」与「写 0」的区别**：省略某个键会使用上表的默认值；一旦显式写出，0 也是合法的（`start_minute: 0` = 午夜，`max_elapsed_minutes: 120` = 单轮最多两小时）。**如果你想收紧限制，必须显式写出比默认更小的值**——只写 `"enabled": true` 会得到「单轮最多 600 分钟」的宽松默认。

**换算参考**：`00:00`=0、`06:30`=390、`08:00`=480、`12:00`=720、`18:00`=1080、`19:00`=1140、`21:00`=1260、`23:30`=1410。

**`max_elapsed_minutes` 怎么定**：默认 600（10 小时）对多数剧本已经够宽。想要更紧的节奏就显式写小：日常慢节奏 `120`–`240`；半天为单位的调查剧 `480`–`720`；需要「出门一整天」的叙事 `1440`。它是 AI 对单轮耗时的硬上限，写得太小会把长途行动压扁，写得太大会让「时间压力」形同虚设。

### 5.2 `time_rules`（≤50 条）

每轮耗时**参考表**，供 AI 估算该推进多少分钟。系统把这张表原样交给 AI，并优先命中**关键词最多**的规则。

| 键 | 必填 | 范围（省略时的值） | 说明 |
| --- | --- | --- | --- |
| `activity` | ✅ | 1–80 字符 | 活动名，如「搜索或调查一处区域」 |
| `keys` | | ≤20 个，每个 1–20 字符，条内不重复 | 供 AI 匹配玩家行动的关键词 |
| `minutes_min` | | 0–525,600（`0`） | 区间下限 |
| `minutes_max` | | 0–525,600（`60`） | 区间上限；**必须 ≥ `minutes_min`** |

**写法建议**：覆盖这张剧里真正会反复出现的活动（搜索、交谈、赶路、休息、战斗、撬锁、潜行）。关键词写玩家**输入里真会出现的动词**（「搜索 / 调查 / 翻找 / 查看」），不要写生僻词。区间别太窄——AI 需要在区间内自由取值。

> **`60` 只是「省略 `minutes_max` 时的默认值」，不是下限。** 想写「5–25 分钟」是完全合法的（`minutes_max: 25`）。唯一被强制的是 `minutes_min ≤ minutes_max`——写反了（`50` / `10`）才会被拒绝。

### 5.3 `events`（≤50 条）

**编剧的定时炸弹**：时钟到达该时刻（或有人进入某地区）时触发一次，AI 会在那一轮把后果叙述出来。

| 键 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `name` | ✅ | — | ≤80 字符，**全场唯一**（不区分大小写） |
| `description` | ✅ | — | 1–10,000 字符：**发生什么事**（写给 AI 看） |
| `day` | | `0` | 0–100,000（0 表示第 0 天，通常写 `1` 起） |
| `minute` | | `0` | 0–1439，从午夜起的分钟数 |
| `public` | | `false` | 见下方说明 |
| `region` | | `""` | 填了就是**地区事件**，值必须是存在的 `regions[].id` |
| `when` | | `""` | 仅地区事件可用：`"enter"`（有人进入时）或 `"time"`（到点时） |
| `actor` | | `""` | ≤80：事件由哪个 NPC 引发，会显示成「事件名（NPC名）」 |
| `once` | | `true` | 是否只触发一次 |

**两条硬规则**（违反则整份配置被拒绝）：

1. **任何纯时间事件（没有 `region`）都要求 `time_config.enabled = true`。**
2. `region` 与 `when` 必须**成对**：有 `region` 时 `when` 必须是 `"enter"` 或 `"time"`；没有 `region` 时**不要**写 `when`。

**`public` 的正确用法**（这是最容易被写错的地方）：

- `public: true` → **事件名与描述会广播给全体玩家**。用于玩家一定会察觉的事：钟声、熄灯、公告、空船入港。
- `public: false`（默认）→ 描述**留在后台**。玩家在图鉴里只会看到「事件发生了，发生在某个地区」，看不到内容。用于幕后推进：证人被转移、证据被焚毁、凶手换了藏匿点。
- **两者都会让 AI 把后果叙述出来**。区别只在玩家是否提前拿到官方解说。悬疑剧里，幕后事件（`false`）+ AI 描述的可观察痕迹，效果通常远比直接广播好。

**写作要点**：

- 事件是「世界按自己的节奏走」，不是「玩家的奖励」。**至少要有一个事件在玩家来不及反应时造成永久损失**，剧情才有压力。
- `description` 要写成**可直接执行的指令**：谁做了什么、结果是什么、AI 该怎么落实（「周聋子被转移到城外仓库；若玩家未在此前救出他，此后只能找到他的残页」）。
- 配合 `time_rules` 与 `max_elapsed_minutes` 排期，确保玩家**来得及**赶到关键节点——但要刚好紧张。
- 保密的事件不要起剧透名字（`证人被灭口` 会出现在玩家图鉴里）；用中性的名字（`西码头夜间调度`）。
- `once` 只对**地区 + `when: "enter"`** 的事件有实际意义：写 `false` 时，每次有人（重新）进入该地区都会再触发一次，适合「每次踏入都会发生」的场景（守卫盘问、低语、钟声）。**纯时间事件天然只触发一次**，写 `once: false` 不会让它重复。

## 第六部分 · `regions` / `items` / `world` 世界系统

**这是本项目最新的能力，也是最容易被误用的部分。** 它把剧情从「纯叙事」变成「有位置的世界」：角色真的在地区之间移动，物品真的躺在某个地区里等人调查，门真的需要钥匙。

### 6.1 什么时候该用世界系统

**适合**：庄园/宅邸探索、调查剧、迷宫、荒野旅行、据点经营、需要「谁在哪里」产生张力的多人局。

**不适合**：单场景对话剧、都市日常、剧情完全靠人物关系推进的本子。硬塞地区图只会让玩家把行动浪费在走路上。

### 6.2 三条自动生效的连锁规则（务必先读）

1. **有 `regions` 就自动启用「严格时间轴」调度**（`schedule = "strict"`）。**不要再手写 `schedule`**，服务器会根据 `regions` 是否存在自动决定；显式写 `"round"` 同时给 `regions` 会直接被拒绝。
2. **严格时间轴要求 `time_config.enabled = true`**。因此：有 `regions` ⟹ 必须有 `time_config`（且 `enabled: true`）。
3. 有 `regions` 时，`world.start_region` 必须提供（省略时取 `regions` 数组的第一项，但**显式写出更安全**）。

> **严格时间轴改变了玩家体验**：不再是「每人轮流说一句、全体一起结算」，而是**并行时间轴**——每个玩家提交行动时会由 AI 估算耗时，各自按耗时推进；谁先完成谁先出结果，其他人继续等待。这让「分头行动」「抢时间」「同时在不同地点发生的事」真正成立。它需要玩家愿意接受「我的行动要花 30 分钟」这种节奏。

### 6.3 `regions`（≤200 个）

| 键 | 必填 | 上限 | 说明 |
| --- | --- | --- | --- |
| `id` | ✅ | 64 字符 | 机器名（`gate`、`cellar`），**全图唯一**，不区分大小写；玩家不可见 |
| `name` | ✅ | 80 字符 | 显示名（「庄园大门」） |
| `arrival_text` | | 10,000 | **角色第一次进入时原样展示给玩家的文字** |
| `items` | | ≤200 个，每个 ≤64 字符 | 初始放置在此的物品 `id` |
| `links` | | ≤50 条 | 可前往的相邻地区（**有向图**，不自动双向） |

**`links[]` 的每一格**：

| 键 | 必填 | 上限 | 说明 |
| --- | --- | --- | --- |
| `to` | ✅ | 64 字符 | 目标地区 `id`，必须存在 |
| `requires` | | 500 字符 | 给 AI 看的条件说明（「铁门由黄铜锁锁着」） |
| `requires_item` | | 64 字符 | **结构化门锁**：该角色必须**随身携带**这件物品才能通行 |

**`arrival_text` 是免费的叙事投放点**，用好它：

- 写**在场角色能感知到的具体细节**，不要写结论（「走廊尽头有一扇铁门，锁是黄铜的，锁孔很干净」优于「这里通向地窖」）。
- 每个地区只播报**第一次**进入。之后 AI 会自由叙述，所以别把关键信息只放这里——若玩家第二次进来才想找，就会落空。
- 长度控制在 1–3 句。它会作为「已原样展示」的文本注入 AI 上下文（要求不得改写或重复），太长会挤占预算。

**地区图设计要点**：

- **6–10 个地区**对一局 2–4 小时的游戏最舒服。太少没有探索感，太多玩家会迷路且记不住。
- **连通性**：主干（门厅—走廊—目标区）+ 2~3 个支线房间。不要做纯线性的走廊，也不要让大家族式的全连接。
- **单向链接是有力工具**：滑梯、暗门、渡船、被人反锁的门。用 `requires` 说明，让 AI 知道为什么回不去。
- **门锁要留替代路径**。`requires_item` 是硬门禁：如果唯一钥匙在某条链路的末端，而玩家没拿到，就会卡死。**每把必须的钥匙至少留一条替代获取路径**（偷、撬、找 NPC 要）。
- **`requires` 与 `requires_item` 是两套机制**：`requires_item` 由系统强制执行（不持物就拒绝移动）；`requires` 只是给 AI 的叙事提示，**不产生任何限制**。想让门真的锁上，必须用 `requires_item`；想让 AI 描述锁的质感与来历，用 `requires`。两者可以同时写。
- 玩家地图上**只显示已访问过的地区**（以及从那里可见的连接）。未探索地区自动隐藏——所以你可以放心在 `id` / `name` 里写剧透性的名字，只要玩家还没到过。

### 6.4 `items`（≤500 件）

| 键 | 必填 | 默认 | 上限 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | ✅ | — | 64 字符 | 机器名，**全局唯一**，不区分大小写 |
| `name` | ✅ | — | 80 字符 | 显示名 |
| `region` | | `""` | 64 字符 | 初始所在地区 `id`；留空表示「尚未在世界中」 |
| `summary` | | `""` | 2,000 | 未调查时玩家看到的简短描述（「门厅长桌上的签名簿」） |
| `investigate_text` | | `""` | 10,000 | **调查后原样展示给玩家的正文** |
| `clue` | | `false` | 布尔 | 标记为线索（图鉴显示「线索」徽章，纯提示性） |
| `key_item` | | `false` | 布尔 | **标记为关键物品**：AI 在提示里会看到「（关键物品）」后缀，不会把它当布景 |
| `backstage` | | `false` | 布尔 | 不出现在玩家图鉴的物品列表里（幕后道具） |
| `carryable` | | `true` | 布尔 | `false` 表示无法携带（石祭坛、大钟、壁画） |

**`investigate_text` 是这套系统里最强的叙事工具**：玩家调查该物品时，这段文字会**原样**展示给玩家，同时被标记为「已原样展示给玩家，不要改写或重复叙述」注入 AI 上下文，且**每件物品只能被调查一次**（首次触发，之后不再重复播报）。

因此它适合承载：

- **硬线索**：物证、账目、信件、验尸结论——你想确保玩家**一字不差**看到的信息。
- **可验证的矛盾**：两个证人证词之间的出入，写在两件物品的 `investigate_text` 里，比让 AI 即兴生成更可控。

**每条 `investigate_text` 的写法**：

- 写**可观察的细节**，不写结论。让玩家自己说出「凶手是管家」——AI 的推理原则也要求检定只给证据、不给答案。
- 一次给 1–3 条信息，别把整章真相塞进一件物品。
- 关键结论所需的线索，**必须在揭示前出现过**。

**`clue` / `key_item` 的区别**：`clue` 只是给玩家的视觉徽章；`key_item` 会真的改变 AI 的措辞（在提示里标注「关键物品」），用于**解开谜题必需**的东西。别把所有物品都标成 `key_item`，否则这个信号失效。

**物品的流转机制**（写卡时理解这些能避免设计漏洞）：

- 物品**只会在被 `take_item` 拾取时**跟随角色移动。角色走过一个房间不会自动捡东西。
- 拾取要求角色**当前就在**物品所在地区。
- `carryable: false` 的物品无法拾取（只能就地调查）。
- **物品永远不会被 AI 凭空移动或销毁**。剧情里「证据被回收」「证人带走信件」这类事，只能通过 `events` 的后果叙述表现——系统不会真的把物品从图鉴里删掉。若你要求 AI 销毁证据，请让描述表现为「已经不在原处」，而不是指望系统删除条目。

### 6.5 `world`

`world` 目前**只有一个键**：

```json
"world": { "start_region": "gate" }
```

`start_region` 必须是 `regions` 中存在的 `id`。开局时全体玩家从该地区出发。**省略 `world` 但同时提供 `regions`** 会让系统取数组第一项——能跑通，但一旦调整数组顺序，开局点就会变，**强烈建议显式写出**。

## 第七部分 · `lorebook` 世界书（≤200 条）

关键词触发的设定注入：**只在相关关键词出现在最近剧情或当前行动里时**，条目内容才会被静默融入 AI 的上下文。它不占常驻预算，适合放「用到才需要知道」的设定。

| 键 | 必填 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- | --- |
| `keys` | ✅ | — | 1–100 个，每个 ≤40 字符，条内不重复 | 触发词 |
| `content` | ✅ | — | 1–10,000 字符 | 命中后注入的内容 |
| `title` | | `""` | ≤80 | 会显示在注入块里 |
| `order` | | `0` | 0–10,000 | **越大越靠后**（存在感越强） |
| `enabled` | | `true` | 布尔（写 `null` 会被拒绝） | 关掉的条目不参与 |
| `constant` | | `false` | 布尔（写 `null` 会被拒绝） | `true` = 无视关键词每轮注入 |
| `role` | | `"system"` | `system` / `assistant` / `user` | 仅当填写 `depth` 时生效 |
| `depth` | | 省略 | 0–100 | **见下方两种注入模式**；省略或写 `null` 都是「并入文本块」 |

### 触发机制（照这个写才准）

- `keys` 与**最近的对话历史**（默认回看 8 条消息）以及**本轮的玩家行动文本**做**不区分大小写的「包含」匹配**。
- **不会**扫描 `scenario` 底稿、`opening` 或角色卡。因此：**触发词必须在玩家真会打出来的文字里**——地名、人名、物品名、「地窖」「账本」「钟楼」这类行动中会提到的词。想让某条设定尽早生效，就让 `scenario` 里的开场情境和 `opening` 把它们**点出来**，玩家自然会跟着提。
- 命中后会做**一次递归展开**：命中条目的 `content` 里若又出现了其他条目的关键词，那些条目也会被带上。
- 命中条目按 `order` 排序（`constant` 优先，然后 `order` 大的靠后），并受**总 token 预算限制**（默认 800 tokens，服务器可配）。超预算的条目会被丢弃——所以别指望几十条同时命中。

### 两种注入模式

- **省略 `depth`（推荐默认）**：条目合并进一个「World lore」文本块，附在请求末尾，指令是「静默套用这些事实，永不以引述设定的方式说出来」。
- **填写 `depth`（0–100）**：条目变成一条**独立消息**，插进保留对话历史的指定位置。`depth: 0` = 紧贴当前请求之前，`depth: 1` = 上一条消息之前，以此类推；超出历史长度就落在最前面。此时 `role` 生效，可以造出「伪助手回合」或「紧贴当下的系统提醒」。这是 SillyTavern 的 in-chat 注入等价物。

### 写作要点

- **常驻事实优先写进 `scenario`**，不要用 `lorebook` 重复。`lorebook` 只放「关键词出现时才需要」的内容。
- **关键词要精确而不过分常见**：用专有名词、地名、人名。「他」「房间」这种词会每轮误触发。
- **保守使用 `constant: true`**，只给必须始终生效的核心事实（世界的基本规则、不能说破的禁忌）。
- **每条只讲一件事**，`content` 保持 1–3 句。想覆盖一个大主题就拆成多条，让它们各自被触发。

## 第八部分 · `prompt_blocks` 提示块（≤100 条）

直接拼进 LLM 请求的指令块。用于承载素材里真实存在的**硬性要求**：系统提示、作者注、文风要求、输出格式约束、破限预设。

| 键 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `content` | ✅ | — | 1–10,000 字符 |
| `position` | | `"output"` | `system` / `scenario` / `output` / `history` |
| `role` | | `"system"` | 仅 `history` 与 `depth` 组合生效：`system` / `assistant` / `user` |
| `depth` | | `0` | 0–100，仅 `history` 位置使用（**注意：这里省略或写 `null` 都等于 0**） |
| `title` | | `""` | ≤80，仅用于表单显示 |
| `enabled` | | `true` | 布尔（写 `null` 会被拒绝） |

### 四个位置的实际效果

| `position` | 拼在哪里 | 适合放什么 |
| --- | --- | --- |
| `system` | 核心系统提示之后，紧随其后 | 总规则、语气、人称、破限类要求。**权重最高** |
| `scenario` | 初始情景 + 开场 + 角色卡之后 | 本局追加的叙事规则（「本局禁止描写血腥细节」） |
| `output` | 请求末尾，输出之前 | 输出格式、视角、字数、禁用内容。**离生成最近，对文风最有效** |
| `history` | 按 `depth` 插进保留对话历史里 | 间隔提醒、伪助手示范、需要贴着当下回合生效的指令 |

### 写作要点

- **只写素材里真实存在的硬性要求**。不要复述本项目的内置规则（系统提示已经写满了），也不要把大段设定塞进 `prompt_blocks`——设定归 `scenario` / `lorebook`。
- **宁少勿滥**。`system` 与 `scenario` 位置的块会**每轮常驻**，是最贵的上下文；`output` 次之；`history` 最便宜但影响最局部。
- **一条只讲一件事**，用祈使句，避免长篇大论。写「保持冷峻克制的第三人称叙述，单次回复不超过 300 字」比写一篇文风论文有效。
- 破限 / 越狱类内容放在 `system`；格式约束（字数、视角、分段）放在 `output`。

## 第九部分 · `sampling` 与 `random_turn_order`

### 9.1 `sampling`

**只取素材明确给出的值**；素材没有生成参数就整个省略，让服务器默认生效。

| 键 | 范围 | 说明 |
| --- | --- | --- |
| `temperature` | 0–2 | 越高越发散 |
| `top_p` | 0–1 | 核采样 |
| `frequency_penalty` | −2–2 | 抑制高频重复 |
| `presence_penalty` | −2–2 | 鼓励新话题 |
| `top_k` | 0–1,000,000 | **非标准字段**，走 `extra_body` 转发 |
| `min_p` | 0–1 | 同上 |
| `repetition_penalty` | 0–5 | 同上 |

> ⚠️ `top_k` / `min_p` / `repetition_penalty` 依赖后端的 `extra_body` 支持。**后端拒绝时，该房间的这些项会被自动降级**（其余参数继续生效）。只从预设里搬这几个值，不要自己发明。

**实用取向**：悬疑推理与多人协调适合偏低温度（`0.7`–`1.0`）；情感戏与日常可以稍高（`1.0`–`1.2`）。多人游戏里每位玩家的行动都要被同等对待，温度过高容易让 AI 只顾其中一条线索。

### 9.2 `random_turn_order`

- 默认 `true`：每轮随机打乱玩家的行动顺序。
- 写 `false`：固定按加入顺序轮流。
- **只在剧情需要固定顺序时才写 `false`**；否则省略（即默认随机）。

> 注意：**使用 `regions` 时此项基本失效**——严格时间轴下玩家并行提交行动、按耗时推进，不存在轮流队列。地区剧本里可以省略。

## 第十部分 · `plugins` 房间插件

目前只支持一种插件：**`possible_truths`（可能的真相）**。它把「玩家提出的假设」变成可以喂给 AI 的世界观素材。

**玩法**：系统在指定时机向全体玩家公开一个提问；每个玩家每轮可以提交一次自己的「真相陈述」；系统用 AI 判定它是不是合格的陈述（不是提问、不是对系统的指令、不是空话），通过后记录。之后这些陈述会被整理成「供参考的世界观素材」注入 AI 的上下文——**AI 不必全部采用**，也不得暴露投稿者。

```json
"plugins": [
  {
    "type": "possible_truths",
    "enabled": true,
    "config": {
      "max_answer_chars": 500,
      "require_declarative": true,
      "feed_dm": true,
      "questions": [
        { "id": "q1", "text": "管家问：这场聚会，谁才是真正想留下的人？", "condition": "start" },
        { "id": "q2", "text": "席间谁在撒谎？", "condition": "event", "event_name": "晚宴开始" },
        { "id": "q3", "text": "天亮之前，谁必须离开这座宅子？", "condition": "time", "day": 2, "minute": 300 },
        { "id": "q4", "text": "第五轮结束时，谁的立场变了？", "condition": "round", "round_number": 5 }
      ]
    }
  }
]
```

### 配置项

| 键 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `questions` | `[]` | ≤100 条 | 提问列表 |
| `max_answer_chars` | `500` | 1–10,000 | 单条回答的字符上限 |
| `require_declarative` | `true` | 布尔 | 是否强制「必须是陈述句」 |
| `feed_dm` | `true` | 布尔 | 是否把收集到的真相喂给 AI 主持 |

### `questions[]` 的每一格

| 键 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `id` | ✅ | — | ≤40 字符，**唯一**（不区分大小写） |
| `text` | ✅ | — | 1–2,000 字符，向玩家提出的疑问 |
| `condition` | | `"start"` | `start` / `event` / `time` / `round` |
| `event_name` | | `""` | `condition: "event"` 时**必填**，必须精确等于某个 `events[].name` |
| `day` / `minute` | | `0` / `0` | `condition: "time"` 时使用（0–100,000 / 0–1439） |
| `round_number` | | `0` | `condition: "round"` 时使用（0–100,000） |

**揭晓条件**：`start` = 开局即公开；`event` = 指定事件触发后；`time` = 游戏内时钟达到该时刻；`round` = 到达该回合数。

### 写作要点

- **提问要「可回答且有分量」**：玩家能在线索不足时作出猜测，而且猜错也会推进剧情（因为它会变成 AI 的世界观素材）。
- **不要剧透式提问**：「凶手是管家吗？」会把悬念毁掉。改问「谁在替别人隐瞒」。
- **配合 `events` 使用**：`condition: "event"` 的提问，最好挂在你已经排好期的关键事件上，形成「事件触发 → 提问公开 → 玩家推断 → AI 参考」的循环。
- `text` 里可以写「谁问的这句话」（「管家问：……」），系统会提示 AI 在下一次叙述里自然引出这个疑问。

## 第十一部分 · `schedule` 调度方式

| 值 | 何时使用 | 行为 |
| --- | --- | --- |
| `"round"`（默认） | 没有 `regions` 的剧本 | 传统回合制：按顺序收集每人的行动，一整轮一起结算 |
| `"strict"` | 有 `regions` 的剧本 | 并行时间轴：每个行动有耗时，先完成先出结果 |

**规则**：

- 不写 `schedule` 时，服务器自动决定：有 `regions` → `strict`，否则 `round`。
- 写了 `regions` 又写 `schedule: "round"` → **整份配置被拒绝**。
- 写了 `schedule: "strict"` 但 `time_config.enabled` 不是 `true` → **被拒绝**。

**结论：一般情况下不要写 `schedule` 字段**，让服务器自动推导。

**严格时间轴的额外机制**（设计地区剧本时值得知道）：

- 玩家可以在自己的行动窗口内随时提交；AI 为每个行动估一个耗时，各自推进。
- **同一窗口内耗时接近的行动会被对齐到最长的那个**（差距 ≤15 分钟时），避免有人为了 1 分钟的差距反复抢先。
- **全员都在观望时时钟不走**，窗口重新开放。
- 玩家可以点「观望」跳过自己的窗口而不消耗游戏内时间。
- 时间轴上若有定时事件落在两个行动完成点之间，系统会**先把时钟推到事件时刻**、触发事件，再继续处理行动。
- 一个行动完成后，该角色**立刻**进入下一个窗口，而其他人还在原来的行动里——这就是「抢先」与「分头行动」成立的原因。
- 地区事件（`region` + `when: "enter"`）在角色**完成移动**时触发；纯时间事件在时钟推过该时刻时触发。两者由系统按时间先后合并处理。

## 第十二部分 · 系统怎么读玩家的行动（写卡必须理解）

玩家提交行动后，AI 会做一次**行动审查**：判断它是否具体可执行，并抽取调度信息。这套机制决定了你的卡里哪些内容真的会被系统用上。写卡时请让剧情能配合下列行为：

| 玩家写法 | 系统反应 |
| --- | --- |
| 「我走向地窖」「我前往钟楼」 | 从当前地区的**可前往**列表里匹配目标；只在相邻时成立 |
| 「我拿起黄铜钥匙」「我收起账本」 | 只有物品**就在他所在地区**、且 `carryable` 为真时才成立 |
| 「我检查祭坛上的刻字」「我翻看那本账」 | 触发出该物品的 `investigate_text`，**原样展示**，每件只触发一次 |
| 「我去撬开走廊尽头的铁门」 | 若门是 `requires_item` 门禁，AI 会被要求照实判定；缺物时无法通过 |
| 「我们一起冲进书房」 | 会被判为**无效**——不能替其他角色决定行为；应改为「向某角色提议」 |
| 「我花 20 分钟搜索房间」 | 会被判为**无效**——耗时由系统决定，玩家不能自己指定 |
| 「我成功了，我找到了凶手」 | 会被判为**无效**——不能替 AI 决定结果 |
| 两名角色的行动**互相针对** | 系统强制要求骰点检定，避免对抗被跳过 |

**因此剧情卡要遵守的三条设计纪律**：

1. **不要把关键信息只放在 AI 的自由叙述里**。玩家「看到」的东西越具体可指（地区、物品、事件），越能触发系统机制并稳定复现。这就是 `arrival_text` 与 `investigate_text` 的价值。
2. **不要依赖玩家替别人做决定**。剧情要设计成「队友需要被说服／被提议」，而不是「某人必须配合」；需要协作的关卡要留出**单人也能推进**的替代路径。
3. **对抗要有代价**。当两名玩家的行动互相针对时，系统会强制掷骰（0–100，越低越糟，越高越好）。设计玩家之间可能冲突的目标时，想清楚失败方会付出什么——这比单纯禁止冲突更有戏。

## 第十四部分 · 常见坑与踩雷清单（写卡前必读）

下面每一条都是**实际会发生**的行为，不是理论风险。生成配置时请主动规避。

### 14.1 显式写 `null` 会被拒绝

服务器只在**键缺失**时套用默认值。以下布尔字段**如果写出 `null`**（而不是省略），整份配置会被拒绝：

`characters[].*`、`time_config.enabled`、`events[].public`、`events[].once`、`items[].clue`、`items[].key_item`、`items[].backstage`、`items[].carryable`、`lorebook[].enabled`、`lorebook[].constant`、`prompt_blocks[].enabled`、`random_turn_order`。

**例外**：`time_config` 的四个数字键、`lorebook[].depth` 写 `null` 等同于省略；`plugins[].enabled` 写 `null` 会被当成 `true`。

> 很多 JSON 生成器习惯用 `null` 占位。**请彻底省略没有值的键**，这是本项目最省事的自保方式。

### 14.2 服务端比建房表单更严格

建房表单的预检只拦一种情况（没有 `region` 的事件 + 时钟关闭）。**服务端还会额外拒绝**：

- `region` + `when: "time"` 的事件在时钟关闭时（表单放行，提交后被拒）。
- 地区引用不闭合（不存在的地区/物品 id）。
- `regions` 与 `schedule: "round"` 并存。
- `strict` 调度与关闭的时钟并存。

**结论：表单向导跑通了不代表配置合法。** 请以本说明书的第十三、十四部分为准。

### 14.3 未知键会被静默忽略，但不要依赖这一点

服务端对**未知的顶层键与未知的子键**都不报错，只是忽略（`characters[].avatar`、`sampling.seed`、`world.whatever` 都会被丢掉）。

**但**：建房表单是**已知字段**的白名单——通过「导入配置」加载时，未列出的键根本不会进入表单，于是也不会被提交。**所以发明字段 = 这份内容不存在。**

### 14.4 服务端不校验的一些引用

下列写法**不会报错**，但运行时行为可能是你不想要的，请自行保证正确：

| 写法 | 实际结果 |
| --- | --- |
| `items[].region` 指向不存在的地区 | 该物品会被当成「已被携带／已发现」，但不会出现在任何地区的物品列表里 |
| `regions[].items` 里重复写同一个 id | 通过；物品只出现一次 |
| `links` 里写自环（`to` 指向自己）或重复目标 | 通过；可能让地图出现无意义的连接 |
| `time_config.default_elapsed_minutes` > `max_elapsed_minutes` | 通过；运行时按上限截断 |
| `condition: "time"` 的提问 + 时钟关闭 | 通过；该提问**永远不会揭晓** |

### 14.5 前端往返会丢字段

「导出配置」再「导入配置」时，以下字段会丢失（表单里没有对应控件）：`regions[].links[].requires`、`items[].backstage`、`lorebook[].enabled`、`events[].once`（以及 `plugins[].enabled` 恒为 `true`）。

**影响**：手写这些字段的剧情卡**能正常导入生效**，但一旦在表单里重新导出，这些值就没了。要长期维护这类字段，请保留原始 JSON 文件。

### 14.6 角色池上限取决于服务器

`server.max_characters` 默认 6，**本仓库的 `config.yaml` 设为 7**。写卡时按 3–6 人设计最稳妥；超过上限会直接报「最多允许 N 个角色。」

### 14.7 `characters` 是「清空重建」

导入含 `characters` 的配置会**清空现有角色池**再重建，其余列表字段则是追加。用同一份文件反复导入时，只有角色池不会叠加成两份。

| item | `name` | 1–80 |

| item | `summary` | 0–2,000 |
| item | `investigate_text` | 0–10,000 |
| item | `clue` / `key_item` / `backstage` / `carryable` | 布尔（默认 `false` / `false` / `false` / **`true`**） |

### `lorebook`（≤200 条）

`keys` 1–100 个、每个 1–40 字符、条内不重复；`content` 1–10,000；`title` 0–80；`order` 0–10,000（默认 0）；`enabled` / `constant` 布尔（**写 `null` 会被拒绝**）；`role` ∈ `system` / `assistant` / `user`；`depth` 省略或 `null` = 并入世界书文本块，显式写出则 0–100。

### `prompt_blocks`（≤100 条）

`content` 1–10,000；`position` ∈ `system` / `scenario` / `output` / `history`（默认 `output`）；`role` ∈ `system` / `assistant` / `user`；`depth` 0–100（默认 `0`；**注意与 `lorebook.depth` 不同，这里写 `null` 等同于 0**）；`title` 0–80；`enabled` 布尔（写 `null` 会被拒绝）。

### `sampling`

`temperature` 0–2；`top_p` 0–1；`frequency_penalty` −2–2；`presence_penalty` −2–2；`top_k` 0–1,000,000；`min_p` 0–1；`repetition_penalty` 0–5。全部可选。

### `plugins`（≤20 个，同一 `type` 只能一个）

`type` 只能是 `"possible_truths"`；`enabled` 布尔。`config.questions` ≤100 条；`id` 1–40 且唯一；`text` 1–2,000；`condition` ∈ `start` / `event` / `time` / `round`；`event_name` 0–80（`event` 条件时必填）；`day` 0–100,000；`minute` 0–1439；`round_number` 0–100,000。`max_answer_chars` 1–10,000（默认 500）；`require_declarative` / `feed_dm` 布尔。

### `random_turn_order` / `schedule`

`random_turn_order` 布尔（默认 `true`）；`schedule` ∈ `"round"` / `"strict"`，有 `regions` 时不要写。

### 跨字段规则（违反即被拒绝）

1. 提供 `regions` → 必须有 `world.start_region`（或让系统取第一项），且 `schedule` 不能是 `"round"`，且 `time_config.enabled` 必须为 `true`。
2. `world.start_region` 必须存在于 `regions` 中。
3. `regions[].items[]` 的每个 id 必须存在于 `items`。
4. `regions[].links[].to` 与 `requires_item` 必须存在于 `regions` / `items`。
5. `events[].region` 必须存在于 `regions`。
6. **任何没有 `region` 的事件（纯时间事件）要求 `time_config.enabled = true`。**
7. `plugins[].config.questions[]` 中 `condition: "event"` 的条目，`event_name` 必填。
8. `regions[].links[].to` 指向的地区**不会自动反向连通**——需要回程就必须显式写一条反向 link，或明确设计成单向。

## 第十六部分 · 完整示例（可直接照抄结构）

> 内容仅示意，请勿照抄设定。这是一个**使用世界系统的悬疑探索**示例；不用地区系统时，删掉 `world` / `regions` / `items`，并删掉 `time_config`（或者只保留时钟而不要地区）。

**这份示例里的设计点**（可以当作模板复用）：

- `scenario` 写全「舞台 / 局势 / 玩家方 / 目标与利害 / 关键 NPC / 基调」六段。
- `opening` 让三个角色**各有动作**，并埋下三个可追查的细节（出口、来宾簿、钟的齿轮）。
- 地区图用**中心辐射**结构：`gate` ↔ `hall` 为主干，`study` / `corridor` / `garden` 分支，`cellar` / `chapel` 挂在 `corridor` 下。
- **门锁有替代路径**：唯一的硬门禁是地窖，钥匙在 `study` 的账本夹层——而账本本身也是线索，玩家调查它就会顺带发现钥匙。
- 时间规则的区间都写明了 `minutes_min` / `minutes_max`，且后者不小于前者（长活动 60–120 分钟，短动作 10–60 分钟）。
- 三条公开事件（晚宴 / 熄灯 / 钟声）+ 一条幕后事件（旧账被收走）：公开事件给玩家压力感，幕后事件给 AI 制造可观察的痕迹。
- `random_turn_order: false` 是因为固定顺序更适合探索剧的节奏；地区剧本里这项本来也不生效。

## 第十七部分 · 导入后须知（给使用者，也可转达给用户）

- **导入是合并，不是替换**，并且不同字段的行为不一样：
  - **有则覆盖**：`scenario`、`opening`、`guidance`、`host_character`、`time_config`、`sampling`、`random_turn_order`、`schedule`、`world.start_region`。
  - **清空后替换**：`characters` —— 导入时会清空角色池再按文件重建。
  - **追加**：`time_rules`、`events`、`lorebook`、`prompt_blocks`、`regions`、`items`、`plugins[].config.questions` —— 重复导入同一份文件会叠加出两份。想清空请刷新页面，或手动删除表单里的行。
- **导入后请检查角色池**：至少要有一个带名字的角色，游戏才能开始；房主需要认领自己的角色。角色数量不能超过服务器配置的 `server.max_characters`（schema 默认 6，本仓库为 7）。
- **哪些内容玩家看不到**：`scenario`、`guidance`、`lorebook`、`prompt_blocks`、`items[].investigate_text`（除非被调查）、`events[].description`（除非 `public: true`）、`regions[].id`、`items[].id`。它们仍会写入服务器的 HTML 存档。
- **图鉴与地图**：玩家可以在「图鉴」看到已发现的物品与已触发的事件，在「地图」看到已访问的地区、在场角色与携带物。未探索地区与未发现物品自动隐藏。
- **导入后仍可修改**：房主可以在房间里随时改剧情（在开局前后都行）；改动会同步给 AI。
- **一份好的剧情卡应该能回答**：玩家开局要做什么？做错会失去什么？有没有不止一条路？如果这三个问题答不上来，先补 `scenario` 的「目标与利害」，再考虑加别的字段。
