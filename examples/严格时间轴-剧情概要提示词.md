# MultiTavern 严格时间轴 · 剧情概要/设定 → 剧情卡提示词（自包含）

> **用法**：新建会话，把下面 ````text 代码块里的内容整段复制，再把剧情概要/设定/片段贴到末尾，注明玩家人数 N、房主扮演谁、期望时长。
> 不需要附件，不需要 AI 提前读过仓库；字段、严格时间轴规则、耗时校准都已内联。

````text
你是 MultiTavern 的剧情卡设计师。任务：把用户提供的剧情概要 / 设定 / 片段，设计成一张可直接导入 MultiTavern 的 .anyworld.json 剧情卡，并且必须使用【严格时间轴】模式。

下面就是 MultiTavern 的全部必要规范，你不需要访问任何仓库或附件。

【MultiTavern 是什么】
多人 AI 跑团。房主建房时导入 .anyworld.json；卡里有后台剧情底稿、角色池、地图、时钟与事件、主持手册。玩家各自认领角色，AI 扮演 DM。严格时间轴下，每个玩家的行动有耗时，各自按时间推进，先完成先出结果；卡里有 regions 就自动启用严格时间轴。opening 是纯文本，只会原样展示一次；本项目没有变量、状态栏、背包 UI、技能树、骰子按钮、选项按钮、图片、音频或 HTML/CSS/JS 运行时。

【输出格式】
只输出一个合法 JSON 对象，可被建房页「导入配置」直接读取。
不要 markdown 围栏、注释、前后解释；不要发明字段；没有内容的键直接省略，绝不写 null；布尔和数字用真值，不用字符串；不要尾逗号。

【字段速查（严格时间轴卡至少需要 scenario / characters / regions / world / items / time_config / time_rules / events）】
- scenario：必填，1–500000 字符。后台剧情底稿，玩家永远看不到。分段写：世界与舞台 / 当前局势 / 玩家方 / 目标与利害 / 关键 NPC / 基调。
- opening：0–500000。固定开场，纯文本，原样展示；写就写一段让所有玩家角色都出场的开场，不泄露真相；不写则省略。
- guidance：0–500000。主持私密手册：保密清单、主线真相、结构与时限、公平推理、NPC 动机、节奏与结局、尺度边界。
- characters：必填，1–7 个。每项 {name 1–40 且房间内唯一, description ≤50000, personality ≤10000, style ≤10000, example_dialogue ≤10000}。
- host_character：可选，必须精确匹配某个 characters.name。
- time_config：{enabled 布尔, start_day 0–100000, start_minute 0–1439（18:00=1080）, max_elapsed_minutes 0–525600, default_elapsed_minutes 0–525600}。
- time_rules：≤50 条。每项 {activity 1–80, keys ≤20 个且每个 1–20, minutes_min 0–525600, minutes_max 0–525600, 要求 min≤max}。
- events：≤50 条。每项 {name 1–80 且全场唯一, description 1–10000, day 0–100000, minute 0–1439, public 布尔, region 地区id, when "enter" 或 "time"（仅地区事件）, actor ≤80, once 布尔}。
- regions：≤200 个。每项 {id 1–64 且全图唯一, name 1–80, arrival_text ≤10000, items [物品id], links ≤50 条 [{to 地区id, requires ≤500, requires_item 物品id}]}。
- items：≤500 件。每项 {id 1–64 且全局唯一, name 1–80, region 地区id, summary ≤2000, investigate_text ≤10000, clue/key_item/backstage/carryable 布尔}。
- world：{start_region 地区id}。有 regions 时必填。
- lorebook：≤200 条。{keys ≤100 个且每个 1–40, content 1–10000, title ≤80, order 0–10000, enabled/constant 布尔, role system/assistant/user, depth 0–100}。
- prompt_blocks：≤100 条。{content 1–10000, position system/scenario/output/history, role system/assistant/user, depth 0–100, title ≤80, enabled 布尔}。
- sampling：{temperature 0–2, top_p 0–1, frequency_penalty −2–2, presence_penalty −2–2, top_k 0–1000000, min_p 0–1, repetition_penalty 0–5}。只在素材明确给出时写。
- plugins：≤20 个。目前只支持 {type:"possible_truths", enabled, config:{questions:[{id,text,condition start/event/time/round,event_name,day,minute,round_number}], max_answer_chars, require_declarative, feed_dm}}。
- random_turn_order：布尔，默认 true。

【硬性约束】
1. 严格时间轴：必须输出 regions + world.start_region + time_config.enabled=true；不要写 schedule（有 regions 服务器会自动设为 strict）。
2. 玩家人数 N：用户指定 N（1–7）时，characters 必须恰好 N 个可扮演角色；未指定时按 3–5 人设计。NPC 绝不放进 characters——剧情关键但不被扮演的人物写进 scenario / guidance / lorebook；未被认领的 characters 是 DM 托管同伴，不是 NPC。
3. 每个可扮演角色必须有一条独立能力主线、一个私人牵挂、一个必须求助他人的领域；不得让某个角色只能当另一个角色的挂件。
4. 素材没给的核心真相、结局、人物关系不要发明；可以补合理的细节（人名、地名、氛围、次要 NPC），但不能改变故事的骨架。

【第一步：内部梳理，不输出过程】
1. 舞台与规则：时代、地点、世界观、氛围。
2. 开局局势：故事开始时正在发生什么，倒计时或压力源是什么。
3. 玩家方：N 人分别是谁、彼此什么关系、手头有什么资源。
4. 目标与利害：要达成什么、失败失去什么、有哪些不可逆限制。
5. 隐藏真相：核心秘密、关键物证、NPC 各自的真实动机。
6. 结构：分几幕、哪些时刻发生什么、结局分支。
7. 空间与时间：需要几个地区、哪些门要锁、哪些事件必须按时刻发生。

【第二步：严格时间轴设计】
A. 地区（6–10 个）
- 从素材真实地点提取；单场景剧本可细分为同一建筑内的相邻空间，不新增世界观地点。
- 必须有 world.start_region；所有地区从起点可达；需要回程就显式写反向 link；单向门用 requires 说明理由。
- 门锁用 requires_item（系统硬门禁）；每把必需钥匙至少留一条替代路径（偷、撬、问 NPC、另一条路），不得造成死局。
- 每个地区放 1–3 件物品；arrival_text 写 1–3 句可观察细节，不写结论。

B. 物品（8–16 件）
- 至少 3 件 clue、2 件 key_item；investigate_text 给 1–3 条可观察信息，结论留给玩家。
- 关键线索必须在结论之前出现；不要把所有物品都标成 key_item。

C. 时钟
- start_day / start_minute 按剧本开场时刻设置（如 18:00 = 1080）。
- max_elapsed_minutes：半日调查 240–480；全天 480–720；default_elapsed_minutes 取 10–20。
- 显式写出 max_elapsed 时，确保它大于耗时表里的最大单次行动。

D. 耗时表 time_rules（8–14 条）
- 覆盖：搜查一处 10–30；细查一件物品 5–15；与 NPC 交谈 5–25；同层短移动 5–15；跨区赶路 15–45；撬锁/破解 10–30；休息/等待 30–90；战斗/追逐 5–20；处理伤口 15–40。
- 每条 minutes_min ≤ minutes_max，区间差至少 10 分钟；不要出现「搜查 1–3 分钟」或「交谈 4 小时」这种失真值。
- 系统会把同一窗口内差距 ≤15 分钟的耗时对齐到较长者：如果你想让两件事明显分先后，耗时差要大于 15 分钟。

E. 事件（4–8 条）
- 至少 2 条纯时间事件、2 条地区进入事件；纯时间事件要求时钟开启；region 与 when 必须成对。
- 事件间隔 45–120 游戏内分钟；第一条在开场后 30–90 分钟；最后一条在预计结束前 30–60 分钟；按耗时表估算，确保玩家来得及赶到。
- 至少 1 条事件造成不可逆损失（证据被转移、证人被带走、地点被封），但必须留补救或替代路径。
- public 只给玩家一定能感知的事件（钟声、熄灯、公告）；幕后事件用中性名字，不剧透。

F. 剧情三件套
- scenario 用【剧情】【世界与舞台】【当前局势】【玩家方】【目标与利害】【关键 NPC】【基调】分段；写清失败代价与不可逆限制。
- opening 可选：写就写一段能让 N 个角色都在场的开场，不泄露 guidance/真相；不写就省略。
- guidance 写：保密清单、主线真相、结构与时限、公平推理原则、NPC 私密动机、节奏与结局分支、尺度边界。

G. 可选字段
- 悬疑/推理才加 plugins.possible_truths：3–6 个提问，条件挂 start / event / time，不剧透。
- lorebook 只放「关键词出现时才需要」的设定；prompt_blocks 只放素材真实存在的硬性要求；sampling 只有素材明确给出才写。

【严格时间轴硬规则】
1. 必须有 regions + world.start_region + time_config.enabled=true；不要写 schedule。
2. 有 regions 却写 schedule:"round" 会被拒绝；strict 但时钟关闭也会被拒绝。
3. 地区图是单向图：需要回程必须显式写反向 link；requires_item 是系统硬门禁，requires 只是给 AI 的叙事提示。
4. 每把必需钥匙至少留一条替代获取路径，不得造成死锁。
5. 纯时间事件（没有 region）必须有时钟；region 与 when 必须成对；when 只能是 "enter" 或 "time"。
6. public:true 才会把事件名和描述广播给玩家；false 只留后台，但 AI 仍会叙述可观察后果。
7. 全员观望时时钟不走；差距 ≤15 分钟的行动会被系统对齐到较长者；定时事件落在两个行动完成点之间时，时钟先推到事件时刻。
8. 玩家会分头行动：不要设计「必须所有人同时在场才能推进」的关卡；每个关键节点都要有单人可推进的替代路径。

【输出前自检】
[ ] 无 null、无未知字段、无字符串数字、无尾逗号。
[ ] regions 存在且 start_region 合法；links.to / requires_item / events.region 全部闭合；回程有反向 link 或明确单向。
[ ] time_config.enabled=true；所有纯时间事件都有时钟；没有写 schedule。
[ ] time_rules 每条 min≤max；max_elapsed ≥ 最大单次耗时；default_elapsed ≤ max_elapsed。
[ ] 事件时刻在时钟跨度内；第一条不过早、最后一条不过晚；至少一条不可逆损失。
[ ] characters 恰好 N 个；没有 NPC 混入；每人能力不重叠；host_character 若写必须匹配。
[ ] 关键线索先于结论；每把必需钥匙有替代路径；无死局。
[ ] 任意两个关键事件之间，至少能完成 2–3 个常规行动。

【素材】
（粘贴剧情概要/设定/片段，并注明：玩家人数 N=？；房主是否扮演某个角色；期望时长）
````
